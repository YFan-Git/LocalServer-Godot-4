一、项目背景与目标

	1.1 问题来源

		Godot 导出的 Web 版项目有一个致命问题：
		浏览器出于安全策略，禁止网页直接访问本地文件系统。
		用户双击 index.html 打开网页后，无法加载游戏资源。

		传统解决方案是使用 Python 的 http.server 模块：
		python -m http.server 8000

		但问题在于：
		- 用户电脑上不一定安装 Python
		- 即使安装了，版本和路径也可能不一致
		- 让普通用户敲命令行不现实

	1.2 项目目标

		开发一个轻量级的本地 HTTP 文件服务器控制器，作为
		"python -m http.server" 的平替方案。

		核心要求：
		1. 不依赖 Python 环境
		2. 双击即可运行（面向普通用户）
		3. 提供图形化控制界面
		4. 启动/停止/浏览器访问一键完成
		5. 适合 Godot Web 导出项目的本地预览


二、技术选型与架构

	2.1 为什么选 PowerShell + HttpListener？

		Python 的方案依赖外部环境，不可行。
		需要找一个 Windows 系统自带的、不依赖额外安装的方案。

		PowerShell 是 Windows 系统自带的脚本环境。
		System.Net.HttpListener 是 .NET 自带的 HTTP 服务器实现。

		优点：
		- Windows 系统自带，无需安装
		- 纯内存运行，无外部依赖
		- 性能足够预览 Godot 项目

	2.2 整体架构

		整个系统分为三层：

		┌─────────────────────────────────────────────────────────────┐
		│                    View 层 (main.gd)                       │
		│  - Godot 图形界面：状态显示、按钮、日志框                  │
		│  - 用户交互：启动/停止/浏览器/清日志                       │
		└─────────────────────────────────────────────────────────────┘
								  │
								  ▼
		┌─────────────────────────────────────────────────────────────┐
		│                Controller 层 (ServerController.gd)          │
		│  - 生成 PowerShell 脚本文件                                │
		│  - 用 Start-Process 启动后台进程                           │
		│  - 管理 PID 文件（启动/停止信号）                          │
		│  - 状态同步与 UI 信号发射                                  │
		└─────────────────────────────────────────────────────────────┘
								  │
								  ▼
		┌─────────────────────────────────────────────────────────────┐
		│                   Model 层 (ServerData.gd)                  │
		│  - SERVER_PS1：完整的 PowerShell HTTP 服务器               │
		│    - 基于 System.Net.HttpListener                          │
		│    - 目录浏览功能                                          │
		│    - 文件服务功能（支持常见 MIME 类型）                    │
		│    - 路径安全检查（防目录遍历）                            │
		│    - 通过 PID 文件实现停止信号检测                         │
		│  - QUIT_PS1：停止脚本                                      │
		└─────────────────────────────────────────────────────────────┘


三、核心设计决策

	3.1 Godot 只做轻量控制，重量工作交给独立进程

		问题：Godot 的 Thread 如果执行包含 while 循环的脚本，
			 线程永远不会结束，Godot 销毁时报警告。

		方案：Godot 不直接执行 server.ps1，
			 而是用 Start-Process 启动一个独立的 PowerShell 进程。

		区别：
		┌─────────────────────────────────────────────────────────────┐
		│ 错误做法（老版本）                    正确做法（新版本）    │
		├─────────────────────────────────────────────────────────────┤
		│ Godot Thread 执行 server.ps1        Godot 执行 Start-Process│
		│ server.ps1 里有 while ($true)       Start-Process 立即返回 │
		│ 线程永远不结束                       while 在独立进程中跑   │
		│ 销毁时报警告                         没有警告，不阻塞       │
		└─────────────────────────────────────────────────────────────┘

	3.2 PID 文件作为进程间通信信号

		问题：Godot 无法直接监控外部进程的退出状态。

		方案：用文件作为信号。
		- server.ps1 启动时，将自己的 PID 写入 server.pid
		- server.ps1 的 while 循环每次检查 server.pid 是否存在
		- stop 时 Godot 删除 server.pid → server.ps1 检测到 → 退出

		这就是"python -m http.server"没有的功能：
		有图形界面控制启动和停止。

	3.3 工作目录的正确处理方式

		问题：最初设计时，试图通过 -workDir 参数传递目录给脚本。
			 但 Start-Process 启动的 PowerShell 进程，
			 默认工作目录就是脚本文件所在的目录。

		错误做法：
		param([int]$port, [string]$workDir)
		Set-Location $workDir
		# 用 $workDir 拼接路径

		问题分析：
		- 脚本生成在 user:// 目录
		- 需要额外传递 -workDir 参数
		- 参数传递容易出错，代码臃肿

		正确做法：
		param([int]$port)
		# 直接用 $PWD，它天然就是脚本所在目录
		$fullPath = [System.IO.Path]::Combine($PWD.Path, $path)

		原理：
		Start-Process 启动 powershell.exe 时，
		新进程的当前目录自动设置为脚本文件所在目录。
		所以 server.ps1 的 $PWD 就是 user:// 目录。

		结论：
		不需要 workDir 参数，直接用 $PWD 即可。
		代码更简洁，更可靠。

	3.4 为什么停止时立即更新 UI

		用户点击停止，期望立即看到反馈。
		删除 PID 文件后，UI 立即变为"已停止"。
		实际的进程清理在后台线程中执行，不阻塞界面。

五、工作流程

	5.1 启动流程

		用户点击"启动"
			  ↓
		检查是否已在运行
			  ↓
		清理旧 PID 文件
			  ↓
		生成随机端口 (8888-9888)
			  ↓
		生成 server.ps1（嵌入端口号）
		脚本中直接使用 $PWD 作为工作目录
			  ↓
		Start-Process 启动后台 PowerShell 进程
		新进程自动以脚本所在目录为工作目录
			  ↓
		UI 状态变为"运行中"

	5.2 服务器运行

		独立 PowerShell 进程：
			  ↓
		HttpListener 监听 localhost:port
			  ↓
		写入 server.pid
			  ↓
		打开浏览器
			  ↓
		while 循环处理 HTTP 请求
		所有路径基于 $PWD 拼接
			  ↓
		每次循环检查 server.pid 是否存在
			  ↓
		不存在 → break 退出

	5.3 停止流程

		用户点击"停止"
			  ↓
		删除 server.pid（触发服务器退出）
			  ↓
		UI 立即变为"已停止"
			  ↓
		后台执行 quit.ps1 清理残留进程

七、关键 Bug 修复记录

	7.1 问题描述

		服务器始终显示错误的工作目录：
		PowerShell 目录服务器 | C:/Users/xxx/AppData/Roaming/Godot/...

		期望的工作目录是 user:// 目录。

	7.2 问题分析

		最初设计中，SERVER_PS1 脚本试图通过 -workDir 参数接收目录：
		param([int]$port, [string]$workDir)
		Set-Location $workDir

		但 ServerController.gd 中调用 get_server_ps1() 时，
		返回的是未定义的 SERVER_PS1 常量（实际定义的是 START_PS1），
		导致生成的 server.ps1 是空文件。

		同时，即使脚本正确，传递 -workDir 参数也非必需，
		Start-Process 启动的进程默认工作目录就是脚本所在目录。

	7.3 正确实现

		1. 确保常量名与调用方法匹配：
		   定义 SERVER_PS1，get_server_ps1() 返回它

		2. 脚本只接收 port 参数，不接收 workDir：
		   param([int]$port)

		3. 直接使用 $PWD 作为工作目录：
		   $fullPath = [System.IO.Path]::Combine($PWD.Path, $path)

		4. 启动命令去掉 -workDir 参数：
		   Start-Process powershell -ArgumentList '-File "server.ps1" -port 8888'

	7.4 修复效果

		服务器启动后，工作目录自动为 user:// 目录，
		优先显示 index.html，没有则显示目录列表。


八、适用场景

	8.1 主要场景

		Godot 游戏开发完成后，导出为 Web 版。
		使用本工具在本地启动 HTTP 服务器，预览 Web 版游戏。
		无需安装 Python，无需敲命令行。

	8.2 次要场景

		任何需要在本地快速启动 HTTP 文件服务器的场景：
		- 前端页面预览
		- 静态文件分享
		- 局域网临时文件服务

十、总结

	本方案是 "python -m http.server" 的 Windows 图形化平替。

	核心价值：
	1. 不依赖 Python 环境，普通用户双击即用
	2. 解决 Godot Web 导出项目无法双击运行的痛点
	3. 图形界面控制，一键启动/停止/打开浏览器
	4. 后台独立运行，不阻塞 Godot 主界面

	技术核心：
	1. PowerShell + HttpListener 实现 HTTP 服务
	2. PID 文件作为进程间停止信号
	3. Godot 只做轻量控制，重量工作交给独立进程
	4. 利用 Start-Process 的默认行为，$PWD 自动为脚本所在目录
	5. 不传递 workDir 参数，代码更简洁可靠
